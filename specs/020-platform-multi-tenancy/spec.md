# Feature Specification: 平台化多租户（Platform Multi-Tenancy）

**Feature Branch**: `020-platform-multi-tenancy`

**Created**: 2026-09-30

**Status**: Draft

**Input**: 当前版本一套部署只能产出一个企业（租户）。数据层与认证层已具备多租户能力，唯一缺口是"租户供给"。本特性补齐租户供给能力，使一套部署可承载多个企业，并新增平台管理员角色专门管理租户生命周期。

---

## User Scenarios & Testing *(mandatory)*

用户故事按优先级排列，每个独立可交付、可测试。

### User Story 1 (P1) — 平台引导：部署检测与创建平台超级管理员

全新部署首次启动时，运维人员通过引导流程完成两件事：查看部署健康状态、创建平台超级管理员。该账号不属于任何企业，只用于管理租户。创建完成后系统即可登录，此时尚无任何企业。

**Why this priority**: 这是整套平台化的入口。没有平台管理员就无法创建任何租户，是所有后续故事的前置。

**Independent Test**: 全新部署启动后访问引导页，可看到各项服务健康状态；填写一个账号即可创建平台管理员并登录。此时租户列表为空。

**Acceptance Scenarios**:

1. **Given** 全新部署且尚未创建平台管理员，**When** 访问系统，**Then** 被定向到引导流程，且引导页是唯一入口
2. **Given** 引导流程步骤 1，**When** MongoDB 不可用，**Then** 明确阻止继续（数据库不可用则无法创建任何账号）
3. **Given** 引导流程步骤 1，**When** MongoDB 可用但向量库/文档处理等其他服务不可用，**Then** 以告警形式展示，允许继续
4. **Given** 引导流程步骤 2，**When** 提交合法账号信息，**Then** 创建平台超级管理员，引导标记为已完成
5. **Given** 平台管理员已存在，**When** 再次访问引导页，**Then** 引导页降级为可选入口，不再强制
6. **Given** 引导完成，**When** 平台管理员登录，**Then** 进入平台控制台，看到"尚无租户"的空状态引导

---

### User Story 2 (P1) — 创建租户（三个字段秒开）

平台管理员在控制台创建企业：只需填写企业名称、租户管理员账号、租户管理员密码即可完成创建。员工账号、大模型、联网搜索、配额等配置全部折叠为可选项，可留待租户管理员后续自行配置。

**Why this priority**: 这是租户供给的核心动作。若强制填写全部配置，每开一个企业都要重走一遍冗长流程，平台化就失去意义。

**Independent Test**: 仅填写三个必填字段即可成功创建一个企业；创建后使用租户管理员账号可登录该企业管理后台，并在其中补充配置大模型等可选项。

**Acceptance Scenarios**:

1. **Given** 平台管理员已登录，**When** 仅填写企业名称 + 管理员账号 + 密码并提交，**Then** 创建成功，返回租户标识
2. **Given** 创建租户表单，**When** 未填写任何可选配置，**Then** 租户仍可创建成功，且该租户配额默认为不限额
3. **Given** 创建租户时，**When** 任一外部依赖服务（向量库、文档处理、对话服务）不可用，**Then** 不影响租户创建
4. **Given** 创建租户时填写了可选的大模型配置，**When** 提交，**Then** 校验通过才创建，校验失败则拒绝并说明原因
5. **Given** 租户创建成功，**When** 查看结果，**Then** 展示租户标识与访问地址，并可继续创建下一个租户
6. **Given** 同一平台内，**When** 创建多个租户，**Then** 各租户标识互不相同，彼此数据互不可见

---

### User Story 3 (P1) — 租户隔离与登录选租户

租户管理员或员工登录时，系统按其所属企业隔离数据。当一个账号同属于多个企业时，登录过程中需明确选择进入哪一个企业。任何租户都无法看到另一个租户的数据。

**Why this priority**: 没有可靠的隔离，多租户就是安全事故。这是平台化的底线要求。

**Independent Test**: 两个租户的同名账号分别登录，各自只见自己企业的数据；一个账号属于两个企业时，登录过程出现企业选择步骤。

**Acceptance Scenarios**:

1. **Given** 登录请求携带了明确的企业标识，**When** 账号密码正确，**Then** 直接进入该企业
2. **Given** 登录请求未携带企业标识且该账号仅属于一个企业，**When** 账号密码正确，**Then** 直接进入该企业
3. **Given** 登录请求未携带企业标识且该账号属于多个企业，**When** 账号密码正确，**Then** 返回候选企业列表供选择，选定后进入
4. **Given** 租户 A 的管理员，**When** 访问任意数据，**Then** 只能看到租户 A 的数据，绝不返回租户 B 的数据
5. **Given** 任一业务请求，**When** 请求上下文缺失企业标识或使用了保留标识，**Then** 一律拒绝，不回退到默认租户
6. **Given** 平台管理员账号，**When** 尝试访问租户内业务接口，**Then** 被拒绝

---

### User Story 4 (P2) — 租户生命周期管理

平台管理员可查看全部租户列表，并对每个租户执行改名、启停、设置成员上限、重置租户管理员密码等操作。列表中只呈现生命周期信息，不呈现租户内部的业务数据（成员数、用量、知识库数量等）。

**Why this priority**: 租户建出来之后需要有管理手段。但明确划清边界：平台方只管生命周期，不看业务数据。

**Independent Test**: 平台管理员可列出并管理租户，且列表中确实不包含任何租户内部业务指标。

**Acceptance Scenarios**:

1. **Given** 平台管理员已登录，**When** 查看租户列表，**Then** 返回全部租户及其状态，可按名称搜索、按状态筛选
2. **Given** 租户列表，**When** 检查返回字段，**Then** 不包含成员数、用量、知识库数等业务指标
3. **Given** 选中某租户，**When** 修改名称或成员上限，**Then** 变更生效并记录审计
4. **Given** 选中某租户，**When** 停用该租户，**Then** 该租户内账号无法登录
5. **Given** 选中某租户，**When** 重置其管理员密码，**Then** 新密码可用，且不强制该管理员首次登录改密
6. **Given** 平台管理员，**When** 尝试查看租户内部业务数据，**Then** 无对应入口与接口

---

### User Story 5 (P2) — 租户归档与恢复

平台管理员可归档不再使用的租户，归档后该租户所有账号禁止登录且不再计入授权数量；需要时可恢复为正常状态，数据完整保留。

**Why this priority**: 企业提供"暂时停用但保留数据"的能力，是运营常态需求，也是彻底清理前的安全缓冲。

**Independent Test**: 归档后该租户账号登录被拒；恢复后数据与配置完整可用。

**Acceptance Scenarios**:

1. **Given** 一个正常租户，**When** 执行归档，**Then** 状态变为已归档，记录归档时间与原因
2. **Given** 已归档租户，**When** 其账号尝试登录，**Then** 一律拒绝
3. **Given** 已归档租户，**When** 统计授权数量，**Then** 该租户不计入
4. **Given** 已归档租户，**When** 执行恢复，**Then** 状态恢复为正常，数据与配置完整可用，账号可正常登录
5. **Given** 归档操作，**When** 完成，**Then** 写入审计记录

---

### User Story 6 (P2) — 租户彻底清理

平台管理员可对**已归档**的租户执行彻底清理，永久删除其全部数据，包括数据库记录、向量数据与磁盘文件。清理不可恢复，执行前需输入企业名称确认。清理后保留一条墓碑记录用于审计追溯，一个月后自动删除。

**Why this priority**: 归档解决"暂时保留"，清理解决"彻底删除"。二者配合才完整。因不可恢复，限定必须先归档再清理。

**Independent Test**: 对已归档租户执行清理后，其数据库记录、向量数据、磁盘文件均被删除，仅剩墓碑记录；对未归档租户执行清理则被拒绝。

**Acceptance Scenarios**:

1. **Given** 一个正常（未归档）租户，**When** 请求彻底清理，**Then** 被拒绝
2. **Given** 一个已归档租户，**When** 请求彻底清理，**Then** 需输入企业名称确认后方可执行
3. **Given** 清理执行中，**When** 查询进度，**Then** 可获取执行进度
4. **Given** 清理成功，**When** 检查各存储，**Then** 数据库记录、向量数据、磁盘文件均已删除
5. **Given** 清理成功，**When** 查看租户记录，**Then** 仅保留墓碑记录（含清理时间），可供审计追溯
6. **Given** 清理过程中任一步失败，**When** 中止，**Then** 租户保持已归档状态并记录失败原因
7. **Given** 墓碑记录超过一个月，**When** 到达清理时间，**Then** 墓碑记录被自动删除

---

### User Story 7 (P2) — 存量部署平滑升级

既有部署（已包含一个企业及其管理员）升级到新版本后，能够补齐平台管理员账号，并将既有企业登记到租户表中，升级后不丢失任何数据，也不要求重新初始化。

**Why this priority**: 存量用户升级后若拿不到平台管理员，将完全无法进入平台控制台，属阻断性问题。

**Independent Test**: 在已有企业的环境上升級，启动后平台管理员可用，既有企业出现在租户列表中且数据完整。

**Acceptance Scenarios**:

1. **Given** 一个已存在企业的部署，**When** 按约定配置了平台管理员凭据并启动，**Then** 自动补齐平台管理员账号
2. **Given** 一个已存在企业的部署，**When** 启动完成，**Then** 既有企业被登记进租户表，数据完整
3. **Given** 存量升级，**When** 重复启动多次，**Then** 登记操作幂等，不产生重复记录
4. **Given** 存量升级但未配置平台管理员凭据，**When** 启动，**Then** 在系统状态中给出明确告警

---

### User Story 8 (P3) — 新租户默认不限额

新创建的租户默认不限制用量额度，企业空间与个人空间两条计量路径均适用。租户管理员后续可按需改为限额。

**Why this priority**: 配额默认值若为零，用户一登录即被拦截。不限额是新租户的安全默认值。

**Independent Test**: 新建租户不做任何配额配置，其成员可正常使用而不被额度拦截；可随时改为限额并生效。

**Acceptance Scenarios**:

1. **Given** 新建租户未配置额度，**When** 其成员使用系统，**Then** 不被额度拦截
2. **Given** 不限额租户，**When** 查询额度，**Then** 明确返回"不限额"标识，不返回需做算术的哨兵数值
3. **Given** 租户管理员，**When** 将额度改为限额并设置数值，**Then** 超出后按预期拦截
4. **Given** 社区版个人空间，**When** 未配置额度，**Then** 同样按不限额处理

---

### Edge Cases

- 部署引导时 MongoDB 不可用 → 阻止继续，其余服务不可用仅告警
- 平台管理员凭据未配置且为全新部署 → 引导页是唯一入口
- 平台管理员凭据未配置且为存量部署 → 系统状态给出告警（否则升级后进不了控制台）
- 账号同属多个企业 → 登录出现企业选择，不允许隐式进入任一企业
- 请求上下文企业标识缺失或为保留值 → 拒绝，绝不回退默认租户
- 归档租户被恢复 → 配置与数据完整还原
- 未归档租户请求彻底清理 → 拒绝
- 清理过程部分失败 → 中止并保持已归档，不半途留下不一致状态
- 墓碑记录满一个月 → 自动删除
- 保留的平台管理标识被当作普通租户处理 → 必须排除，不得为其创建组织与岗位角色
- 存量升级重复启动 → 幂等，不重复登记

## Requirements *(mandatory)*

### Functional Requirements

**租户供给**

- **FR-001**: 系统 MUST 提供创建租户的能力，必填项仅限企业名称、租户管理员账号、租户管理员密码
- **FR-002**: 系统 MUST 允许在创建租户时跳过员工账号、大模型、联网搜索、配额等配置
- **FR-003**: 创建租户 MUST NOT 依赖任何外部服务的可用性，仅依赖数据库可写
- **FR-004**: 系统 MUST 为每个租户生成全局唯一且不可猜测的租户标识
- **FR-005**: 创建租户 MUST 同时建立该租户的管理员账号、根组织与内置权限角色

**平台管理员**

- **FR-006**: 系统 MUST 提供独立于任何企业的平台管理员账号
- **FR-007**: 平台管理员 MUST 通过首次启动引导流程创建，且 MUST 支持通过环境配置预置以供无界面部署与存量升级使用
- **FR-008**: 平台管理员 MUST ONLY 访问租户生命周期管理功能，MUST NOT 访问租户内部业务数据
- **FR-009**: 系统 MUST 仅支持一个平台管理员账号
- **FR-010**: 平台管理员凭据重复初始化 MUST 幂等

**引导流程**

- **FR-011**: 系统 MUST 在首次启动且无平台管理员时强制进入引导流程
- **FR-012**: 引导流程 MUST 展示部署健康状态，其中仅数据库不可用会阻止继续，其余服务异常仅告警
- **FR-013**: 引导流程 MUST NOT 创建任何租户
- **FR-014**: 平台管理员已存在时，引导流程 MUST 降级为可选入口

**登录与隔离**

- **FR-015**: 系统 MUST 支持登录时指定企业标识
- **FR-016**: 账号属于多个企业时，系统 MUST 要求明确选择企业后进入
- **FR-017**: 系统 MUST NOT 在缺少企业标识时回退到任何默认企业
- **FR-018**: 租户间数据 MUST 完全隔离，任一租户无法访问其他租户数据
- **FR-019**: 系统 MUST 拒绝以平台管理标识访问租户业务接口

**生命周期管理**

- **FR-020**: 平台管理员 MUST 能够列出全部租户，支持名称搜索与状态筛选
- **FR-021**: 租户列表 MUST NOT 包含租户内部业务指标
- **FR-022**: 平台管理员 MUST 能够改名、启停租户并设置成员上限
- **FR-023**: 平台管理员 MUST 能够重置租户管理员密码，且 MUST NOT 强制其首次登录改密
- **FR-024**: 平台管理员 MUST 能够归档租户，归档后该租户所有账号 MUST 被禁止登录
- **FR-025**: 已归档租户 MUST NOT 计入授权数量
- **FR-026**: 平台管理员 MUST 能够将已归档租户恢复为正常状态，且数据完整保留
- **FR-027**: 所有生命周期操作 MUST 写入审计

**彻底清理**

- **FR-028**: 彻底清理 MUST 仅对已归档租户可执行
- **FR-029**: 彻底清理 MUST 要求操作者输入企业名称作为确认
- **FR-030**: 彻底清理 MUST NOT 需要第二人审批
- **FR-031**: 彻底清理 MUST 删除该租户的数据库记录、向量数据与磁盘文件
- **FR-032**: 彻底清理 MUST 提供进度查询
- **FR-033**: 彻底清理部分失败 MUST 中止并保留已归档状态，记录失败原因
- **FR-034**: 彻底清理成功后 MUST 保留墓碑记录，并在一个月后自动删除

**配额**

- **FR-035**: 新租户的配额默认值 MUST 为不限额
- **FR-036**: 不限额 MUST 同时覆盖企业空间与个人空间两条计量路径
- **FR-037**: 查询额度 MUST 返回明确的不限额标识，而非需要算术的哨兵数值
- **FR-038**: 租户管理员 MUST 能够将不限额改为限额

**存量升级**

- **FR-039**: 升级后 MUST 自动将既有企业登记到租户表，且 MUST 幂等
- **FR-040**: 存量升级未完成平台管理员配置时，系统 MUST 在状态中给出告警

### Key Entities

- **平台管理员（Platform Admin）**: 不属于任何企业的管理账号，仅用于租户生命周期管理；全局唯一。
- **租户（Tenant）**: 一个企业实例。属性：租户标识、企业名称、状态（正常/停用/已归档/已清理）、版本类型、成员上限、租户管理员账号名、创建来源、创建时间、归档时间与原因、清理时间。
- **租户管理员（Tenant Admin）**: 归属于某个租户的管理账号，负责该租户内部全部配置与业务数据。
- **组织档案（Organization）**: 租户内部的组织属性与业务配置，与租户一一对应，承载计费、成员限制等。
- **配额策略（Quota Policy）**: 租户的用量额度策略，含是否不限额、周期、时区、状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 创建一个新租户所需填写的必填字段不超过 3 个，全流程无需等待任何外部服务连通
- **SC-002**: 新建租户在零可选配置的情况下即可完成创建，其成员可正常使用而不被额度拦截
- **SC-003**: 跨租户数据访问测试全部通过：任一租户在任意接口下均无法读取到其他租户的数据
- **SC-004**: 存量部署升级后，既有企业 100% 被登记且数据零丢失，平台管理员可用
- **SC-005**: 彻底清理执行后，该租户的数据库记录、向量数据、磁盘文件残留均为 0
- **SC-006**: 归档租户恢复后，配置项与业务数据 100% 可用
- **SC-007**: 全部租户生命周期操作（创建/改名/启停/归档/恢复/清理/重置密码）均有审计记录可追溯
- **SC-008**: 首次启动引导在仅有数据库可用的情况下也能完成（其余服务不可用时仅告警）

## Assumptions

- 既有数据模型已按租户标识分区，认证层已支持指定租户登录与多租户选择，本特性不重建这两层，只补齐供给能力。
- 平台化后，"首次启动引导"与"创建租户"是两个独立动作，引导不代劳创建第一个租户；以控制台空状态引导替代。
- 平台管理员与既有"启动时预置管理员"是不同角色：后者创建的是租户内管理员，本特性需将两组配置命名区分以避免混淆。
- 按租户数计费/授权的机制当前尚未实现，本特性只约定"归档不计入"的统计口径，为将来预留。
- 彻底清理为高危操作，假定由受信任的平台管理员执行；因此采用"先归档后清理 + 输入名称确认"作为防护，不引入多审批人流程。
- 保留一个专用租户标识用于平台管理员，该标识在任何按租户枚举的逻辑中都必须被排除。
