# Feature Specification: Session-Level Versioning, Handoff & Collaboration

**Feature Branch**: `002-session-versioning`

**Created**: 2026-07-08

**Status**: Draft

**Input**: 为 MOGO 的 Agent 会话引入会话级版本管理与交接：commit 保存进度、log 回看历史、resume 续写且永不分叉、share 链接交接需求/讨论/执行上下文、多人共用同一会话上下文、会话保存/分享时自动低熵秘密过滤。补齐 GAP 分析 2.6（AgentGit 会话级已验证方向，MOGO 当前空白）。

## User Scenarios & Testing *(mandatory)*

用户故事按优先级排列，每个独立可交付、可测试。

### User Story 1 (P1) — 会话进度快照与回看（commit / log）

用户或 Agent 可以在会话进行中的关键节点"提交"一个进度快照（commit），随后可以按时间线回看所有快照（log），每个快照包含：快照时间、触发者（用户/Agent/自动规则）、会话上下文摘要（最近 N 条消息、工作区文件状态引用）、变更说明。

**Acceptance Scenarios:**
- 用户手动 commit → 生成带说明的快照，log 中按时间倒序可见
- Agent 在工具执行成功后自动 commit（可配置触发规则）→ log 中标注触发源
- log 回看任意快照 → 可预览该时刻的上下文摘要（非全量导出）
- 无任何快照时 log 为空态，引导用户首次 commit

### User Story 2 (P1) — 续写会话且永不分叉（resume）

任意用户（在可见性范围内）可以从最近一个 commit 或最新状态"续写"会话（resume），沿原会话继续，不产生平行分支；会话历史是一条线性时间线，resume 点之后的新消息追加在末尾。

**Acceptance Scenarios:**
- 用户 A commit 后离开，用户 B resume 该会话 → B 从 A 的 commit 点继续，历史不变
- 同一时刻两个用户都 resume → 以先到者为准，后到者读取最新状态（线性追加，无分叉）
- resume 后继续产生的消息归入同一会话 ID，log 时间线连续

### User Story 3 (P1) — 会话交接链接（share）

会话所有者生成 share 链接，把需求、讨论、修改过程与执行上下文一并发给接手人；接手人打开链接补充最新要求后，沿原会话继续工作，而非从头再开一个会话。

**Acceptance Scenarios:**
- 生成 share 链接 → 接手人（组织内授权）打开即见会话上下文（脱敏后）
- 接手人补充要求并 resume → 原会话时间线追加，可追溯"谁在哪个快照点接手"
- share 链接可设置有效期与可见范围（仅指定成员/全组织）
- 未授权用户打开链接 → 拒绝并记录访问审计

### User Story 4 (P2) — 多人共用同一会话上下文（co-presence）

组织内多名成员可同时进入同一会话，围绕同一上下文协作：各自发言、共同查看执行过程；会话对协作成员保持在线可读，冲突遵循 Story 2 的线性追加规则。

**Acceptance Scenarios:**
- 两名成员同时在会话中发言 → 消息按时间线性合并，顺序不丢失
- 成员离开/加入 → 会话状态对其他成员透明可恢复
- 协作成员默认只读历史消息，新增消息受会话权限控制

### User Story 5 (P2) — 会话保存/分享时秘密过滤

会话在保存（commit）与分享（share）时自动执行低熵秘密识别：疑似密钥、令牌、连接串等字段替换为可逆占位符（仅会话所有者与管理员可解引用），clone/导出默认只读；运行时的 PII 脱敏（特性 001 层 3）与保存时过滤形成"运行时 + 保存时"双保险。

**Acceptance Scenarios:**
- 会话中出现 API key 样式的长随机串 → commit 时自动替换为占位符，log 中只显示占位符
- 占位符可由所有者在授权界面解引用查看原值（操作留审计）
- share/clone 出去的副本默认只读，且不含可解引用能力
- 低熵识别误报（如普通长文档 ID）→ 提供白名单与手动标记机制

### Notes / Assumptions
- 本特性补齐 docs/MOVO企业级智能体功能补强规划.md "二、GAP 分析 2.6 会话级版本管理与交接"，并与"三、功能补强清单 6. 会话/工作流双版本化"对齐
- 会话版本化是"工作上下文"的版本化；工作流（流程定义）的版本化属后续范围，本特性不涉及 GraphSpec
- commit 是显式快照 + 规则自动触发，不是每条消息都版本化（控制存储成本）
- 线性时间线是硬约束：resume 永不分叉（与 AgentGit resume 语义一致）
- 秘密过滤的可逆性仅限本系统内授权解引用，不提供跨系统导出明文
- 与特性 001（gatekeeper）的审批/审计体系共用同一审计落点

## Functional Requirements

- FR-1: 会话支持创建进度快照（commit），快照包含时间、触发者、上下文摘要、变更说明；触发方式 = **手动 commit + 规则自动触发（触发条件：会话 idle 超时 / 用户显式"保存" / 关键工具调用后，可配置）**
- FR-2: 快照列表（log）按时间线可回看，支持预览任意快照的上下文摘要
- FR-3: resume 从指定快照或最新状态继续会话；**恢复后消息 seq 从该快照最大 seq 续编（不重置）**，会话历史保持线性时间线，永不产生分叉
- FR-4: 同一会话的并发续写以先到者为准，后到者自动读取最新状态；**seq 冲突用 MongoDB 乐观锁（`seq` 字段 CAS，冲突者重读最新 seq 重试，最多 N 次后 fail-closed）**
- FR-5: share 链接携带会话上下文交接，支持有效期与可见范围设置；**交接后交接者保留只读访问，接手者获得编辑权（可见范围由 006 RBAC 权限码控制）**；**share 失效（过期/被取消）后访问者看到"链接已失效"空态，不可再读**
- FR-6: 多人可同时进入同一会话，消息按时间线性合并；**部分成员离线时其已合并的贡献保留在会话历史，co-presence 在线态仅反映当前在场成员（不阻塞离线成员的历史贡献）**
- FR-7: commit 与 share 时自动执行低熵秘密识别，**判定 = Shannon 熵 ≥ 3.5 bits/char 且长度 ≥ 16 叠加正则前缀（`sk-`/`ghp_`/`AKIA`/`Bearer `）双判定，疑似秘密替换为可逆占位符**
- FR-8: 占位符仅会话所有者与管理员可解引用；**"解引用" = 将可逆占位符还原为原秘密明文（仅会话所有者/全能力管理员，且仅本系统内，不提供跨系统导出）**，解引用操作记录审计
- FR-9: 会话副本（clone）与分享内容默认只读
- FR-10: 秘密识别支持白名单与手动标记，降低误报
- FR-11: 会话级事件（进入/离开/commit/resume/share/解引用）全部写入既有审计通道；**审计字段含 操作者/时间/会话 ID/事件类型/引用对象（解引用时含被还原占位符 ID）**
- FR-12: **快照存于独立 collection `session_snapshots`（不内嵌 session 文档），附件（大文件/二进制）存既有存储并仅存引用指针，快照本身不含附件二进制**；**co-presence 在线态首期不引入 Redis，用 MongoDB 会话状态 + 短轮询**

## Non-Goals
- 不实现工作流（流程定义）版本化与 GraphSpec 契约（双版本化中的工作流级，后续特性）
- 不实现工作流灰度/回滚/执行轨迹回放
- 不实现跨组织会话共享
- 不改变 DSH 运行时单会话内的 Agent 执行语义（版本化作用于会话状态层）
- 秘密可逆占位符不提供系统级导出/跨实例同步能力

## Success Criteria
- 会话交接后接手人无需重新描述需求即可继续工作（交接成本下降的定性验收 + 快照可恢复率 100%）
- resume 后历史时间线连续性 100%（无任何分叉记录）
- 含秘密样本的会话 commit 后，log/share 视图中明文秘密出现次数为 0
- 并发写入消息顺序一致性 100%（无丢失、无乱序）
- 解引用操作 100% 可审计追溯

## Clarify 记录（/speckit-clarify，2026-07-08）

### OQ-1 快照存储结构
- **决策**：快照用独立 collection `session_snapshots`，不内嵌 session 文档。
- **依据**：会话消息量大，内嵌会使 session 文档膨胀（现有 `doc["versions"]` 仅保留最近 12 版即为此考量）；快照需独立查询/导出，独立集合更利于索引与分页。

### OQ-2 低熵秘密识别阈值
- **决策**：Shannon 熵阈值 ≥ 3.5 bits/char 且长度 ≥ 16 触发"疑似秘密"，叠加正则前缀特征（`sk-`/`ghp_`/`AKIA`/`Bearer ` 等）双判定，降低普通长文档 ID 误报。

### OQ-3 co-presence 是否引入 Redis
- **决策**：首期不引入 Redis，co-presence 在线态用 MongoDB 会话状态 + 短轮询；Redis 作为后续可选加速。
- **理由**：自托管已依赖 MongoDB，首期 co-presence 低频（进出/发言），轮询足够；与 001 OQ-2"能不加 Redis 就不加"同源。

### OQ-4 share 链接鉴权模型
- **决策**：share 用短时效 token + 组织内可见范围，与 006 RBAC 权限码联动，不另起鉴权体系。

## 跨特性关系（被依赖方视角，2026-07-08 双向声明）

- **与 001（gatekeeper）**：002 的会话级事件（进入/离开/commit/resume/share/解引用）进 001 的审计落点；会话交接的授权复用 001 权限码模型（见 001 spec）。
- **与 009（hooks-interception）**：002 的会话生命周期事件（SessionStart/SessionEnd/MemoryCommit）**经 009 钩子触发**——002 提供事件语义，009 提供钩子挂载点。
- **与 011（dream-cycle）**：002 的会话快照（`session_snapshots`）是 011 自进化的**经验来源之一**（011 从会话 commit/沉淀中提取经验片段）。
- **与 013（multi-im-entry）**：002 的会话模型**可承载 IM 渠道会话**——IM 会话经 `im_session_bindings` 映射为 MOGO 会话，渠道标识（channel/channel_session_id）存于绑定表，002 的 commit/share 对 IM 会话同样生效。
- **与 017（three-scope-memory）**：002 的会话沉淀（FR-5）**可产记忆**——会话结束时按范围沉淀为 017 的 personal/workspace 记忆。
- **与 005（knowledge-rag）边界**：002 的 share 交接的是**会话上下文（工作状态）**，005 分享的是**知识（可检索资产）**，二者不同层（会话 vs 知识），不混淆。
