# Feature Specification: Deployment & Release Hardening（部署与发布加固）

**Feature Branch**: `024-deployment-hardening`

**Created**: 2026-10-11

**Status**: Draft

**Input**: QualityForge 审计（`.qualityforge/QUALITYFORGE-REPORT.md`），部署与发布范围共 **42 个 P0/P1 缺陷：1 项 fail（QF-818）+ 41 项 blocked**，覆盖部署安全（QF-816~824）、制品与可追溯性（QF-811~817）、灰度与回滚（QF-825~832）、特性开关与发布管理（QF-828/833~835）、持续运行与灾备（QF-836~860）。相邻的发布流程项 QF-021（破坏性变更迁移说明）、QF-024（发布制品一键安装验证）一并纳入。

> **重要口径**：42 项中 **41 项为 `blocked`**，含义是"该能力**尚未建立任何基础设施**，因此无法验证"，不是"验证失败"。本特性的主体工作是**建立基础设施**（脚本、配置、流水线、文档、演练），而非修补已存在逻辑。唯一 `fail` 项 QF-818（镜像以 root 运行）是当前唯一的实证缺陷。

---

## User Scenarios & Testing *(mandatory)*

用户故事按优先级排列，每个独立可交付、可测试。

### User Story 1 (P1) — 部署安全基线

现有部署中，三个 Python 服务（`chat-api` / `admin-api` / `document-parser`）与 `gateway` 的 Dockerfile 均无 `USER` 指令，`docker-compose.yml` 中 `user:` / `read_only:` / `cap_drop:` / `no-new-privileges:` 出现次数为 **0**，即全部容器以 root 运行、文件系统可写、持有全部内核能力。配置则散落在 `.env` 与各服务配置类中，无清单、无变更审计、无漂移检测。

本故事建立最小部署安全基线：非 root、只读文件系统、最小内核能力、配置与代码分离、配置清单可枚举、配置变更可审计可回滚、手工变更可检出。

**Why this priority**: 这是其余所有故事的底座。非 root 是唯一实证缺陷（QF-818 fail），也是容器逃逸到宿主的直接路径。基线不建立，后续灰度/回滚/灾备都建立在不可信的运行环境上。

**Independent Test**: `docker inspect` 任一运行中容器，`User` 字段非 `0`；`ReadonlyRootfs` 为 `true`；`CapDrop` 包含 `ALL`；配置清单文件与服务代码中的读取点一一对应，可审计出一条配置变更的历史。

**Acceptance Scenarios**:

1. **Given** 任一服务镜像（`chat-api` / `admin-api` / `document-parser` / `gateway` / `admin-web` / `user-web`），**When** 构建完成，**Then** 镜像包含非特权用户且在启动前切换，`docker run` 默认以非 root 身份运行
2. **Given** 运行中的业务容器，**When** `docker inspect` 检查，**Then** `ReadonlyRootfs=true`，写入路径仅限显式挂载的 `tmpfs` 或命名卷，且各自限定用途
3. **Given** 运行中的业务容器，**When** `docker inspect` 检查，**Then** `CapDrop=["ALL"]`，仅挂载所需的最小 `CapAdd`，且 `NoNewPrivileges=true`
4. **Given** 运行镜像，**When** 检查镜像层内容，**Then** 不含构建工具（`gcc` / `pip build` 依赖）、测试文件与源码缓存
5. **Given** 仓库中存在配置清单，**When** 比对代码中的配置读取点，**Then** 每个配置键在清单中有登记，每个登记项在代码中有读取点
6. **Given** 修改任一环境配置，**When** 执行部署，**Then** 变更被记录（操作者、时间、旧值→新值、受影响服务），并可回滚到任一历史版本
7. **Given** 有人在宿主机手工 `docker exec` 改了一个卷内文件，**When** 运行漂移检测，**Then** 该变更被检出并报告差异
8. **Given** 任一服务的配置中存在未登记于清单的必填键，**When** 部署，**Then** 部署被拒绝并指出缺失键名

### User Story 2 (P1) — 制品与可追溯性

QF-811~815 在审计中已 `pass`（制品与流水线一致、带版本与提交标识、各环境同制品、配置与代码分离、缺失配置启动失败）。本故事的增量是：把这套**已被验证的实践固化为强制门禁**，补齐环境配置差异枚举（QF-816 blocked）、配置变更审计（QF-817 blocked）、部署计划预审（QF-823 blocked）与手工变更检出（QF-824 blocked），并让发布制品可从发布说明一键安装验证（QF-024 blocked）。

**Why this priority**: 可追溯性是灰度与回滚的前提——无法确定线上跑的是哪份产物，就无法定义"回滚到哪里"。这一层大部分能力已存在，成本低、收益直接。

**Independent Test**: 取线上任一容器的镜像 digest，能在流水线的发布记录中反查到同一 digest 及其对应 git commit；删除一个必填配置键后启动失败并在日志中指明该键名。

**Acceptance Scenarios**:

1. **Given** 线上运行的任一容器，**When** 取出其镜像 digest，**Then** 可在流水线发布记录中反查到同一 digest 与对应 git commit，二者不匹配则告警
2. **Given** 任一制品，**When** 查看其标签与元数据，**Then** 含语义化版本号、git commit SHA、构建时间，三者齐全
3. **Given** 同一制品部署到 dev 与 prod，**When** 比对两环境，**Then** 镜像 digest 完全一致，差异仅存在于配置层
4. **Given** 删除一个必填配置键，**When** 启动服务，**Then** 进程以非零码退出，日志指明缺失的键名与期望取值范围，不进入半初始化状态
5. **Given** 一次计划中的部署变更，**When** 执行 dry-run，**Then** 产出计划 diff 供预审，实际执行结果与计划一致，任何偏离被报告
6. **Given** 一份发布说明，**When** 按说明在干净机器上安装，**Then** 可一键完成安装并通过最小可用性验证
7. **Given** 有人在宿主机手工修改了容器配置或卷内容，**When** 运行漂移检测，**Then** 该未纳管变更被检出并标记
8. **Given** 制品晋级（candidate → promoted），**When** 查看流水线记录，**Then** 有明确的晋级动作、执行者与时间

### User Story 3 (P1) — 灰度与回滚

当前部署模型为单机 Docker Compose 一次替换全部服务实例，不存在灰度通道，也不存在"新版本失败自动切回旧版本"的能力。QF-825~832 全部 `blocked`。`scripts/test_backup_restore_rollback.sh` 已覆盖"备份 → 升级 → 回滚"的函数级演练（Docker 调用被 mock），但那是**版本回退演练**，不是**灰度发布 + 指标驱动自动回滚**。

本故事建立灰度通道（新旧版本并存 + 按比例分流）、观察窗口与指标对比、自动回滚条件、真实回滚演练、数据变更与代码回滚的兼容性结论。

**Why this priority**: 灰度与回滚直接决定"出错时能否止血"。这是从"能发布"到"敢发布"的分界线，且 QF-827（自动回滚条件）与 QF-831（回滚耗时）是 P0。

**Independent Test**: 发布新版本到 10% 流量，观察窗口内新旧版本指标可并排对比；人为注入错误率超阈，自动回滚在约定时限内触发并完成；演练记录可查。

**Acceptance Scenarios**:

1. **Given** 一次新版本发布，**When** 进入灰度阶段，**Then** 流量按比例推进（默认 1% → 10% → 50% → 100%），每档有观察窗口与校验点
2. **Given** 灰度进行中，**When** 查询指标，**Then** 新旧两个版本在同一维度（错误率、延迟、吞吐）可并排对比
3. **Given** 灰度观察窗口内错误率或延迟超过预设阈值，**When** 达到观察时长，**Then** 自动回滚被触发，无需人工介入
4. **Given** 自动回滚条件定义文档，**When** 在预发环境执行，**Then** 条件被实际触发并验证过，验证记录可查
5. **Given** 一次代码回滚，**When** 检查其依赖的数据变更，**Then** 有明确的兼容性结论：可回滚 / 不可逆，不可逆项需迁移脚本兜底
6. **Given** 一次回滚演练，**When** 演练完成，**Then** 记录实测耗时，且实测值 ≤ 约定目标
7. **Given** 回滚完成，**When** 检查关键指标，**Then** 错误率、延迟、可用性恢复至回滚前基线，并有校验记录
8. **Given** 一次发布计划声明了数据库变更，**When** 执行代码回滚，**Then** 数据库变更按兼容性结论处理，不产生数据损坏

### User Story 4 (P1) — 特性开关与发布管理

当前无特性开关机制，发布过程依赖 `docs/release-process.md` 与 `docs/open-source-productization/release-checklist.md` 的人工检查单，但检查单**不覆盖自托管企业部署的配置差异与依赖差异**，且没有"每项有执行人与结论"的强制记录。数据库变更无"先于代码"的顺序约束，破坏性变更无扩展-收缩流程。QF-828 / QF-833 / QF-834 / QF-835 全部 `blocked`。

**Why this priority**: 灰度与回滚（US3）的实际收益取决于"能否把变更切小、能否让数据库不阻塞"。特性开关是把变更切小的唯一手段；发布检查单是把所有约束变成可执行门禁的唯一手段。

**Independent Test**: 一个后端能力可通过特性开关单独开启/关闭而不重新部署；一次涉及 schema 变更的发布，数据库变更先落地且不影响线上服务，代码回滚后旧版本仍能工作。

**Acceptance Scenarios**:

1. **Given** 一个功能特性，**When** 查询其特性开关，**Then** 有属主、默认值、到期日期与清理计划四项登记
2. **Given** 一个特性开关已到期，**When** 运行清理检查，**Then** 发出告警，提示属主处理残留代码分支
3. **Given** 一次包含数据库变更的发布，**When** 执行，**Then** 数据库变更先于依赖它的代码落地
4. **Given** 一个破坏性 schema 变更，**When** 规划，**Then** 使用扩展-收缩流程：先扩展并双写、再切换读写、最后收缩，三个版本兼容
5. **Given** 一次迁移执行中，**When** 线上持续有请求，**Then** 迁移不阻塞线上服务，长事务被拆分或异步执行
6. **Given** 一份发布检查单，**When** 发布前检查，**Then** 覆盖配置差异（各环境）与依赖差异（镜像 digest、运行时版本）
7. **Given** 检查单每项，**When** 发布评审，**Then** 有执行人姓名与明确结论（通过 / 不适用并说明原因）
8. **Given** 一个标记为"不适用"的检查项，**When** 复核，**Then** 必须有理由说明，否则视为未通过

### User Story 5 (P1) — 持续运行与灾备

当前具备：`mogo backup` / `mogo restore`（`deploy/cli/backup.sh`，归档 8 个命名卷 + SHA256SUMS + 版本/commit 标记）与 `scripts/test_backup_restore_rollback.sh` 的 mock 演练；QF-837（备份可恢复并通过业务校验）已 `pass`。缺口是：**没有自动备份策略**、备份**未加密**、无保留策略、单区单机（QF-840~843）、无书面 DR 预案（QF-844~847）、证书**手工放置无续期告警**（`deploy/tls/README.md` 要求手工拷贝 `fullchain.pem`，QF-848~850）、无水位告警与容量模型（QF-854~857）、无值班表与告警升级路径（QF-858~860）。

**Why this priority**: 这一组全部是 P0/P1 且全部 blocked，是本特性中工作量最大、"缺基础设施"最彻底的部分。首期以**单区域 + 可验证备份恢复 + 完备 DR 预案与演练**达成 RTO/RPO 承诺，把跨可用区与自动扩缩容留到后续。

**Independent Test**: 从最近一次自动备份恢复到一台干净主机，业务校验通过；单区故障（拉掉整台主机）后在 RTO 内恢复服务；DR 预案文档含 RTO/RPO 目标与上次演练的实测值。

**Acceptance Scenarios**:

1. **Given** 备份策略已配置，**When** 到达备份周期，**Then** 备份自动执行，最近一次成功时间在约定窗口内
2. **Given** 一次备份失败，**When** 失败发生，**Then** 触发告警，并在平台可查询失败记录
3. **Given** 一个备份集，**When** 检查其内容，**Then** 已加密，访问受控（仅授权身份可解密）
4. **Given** 备份保留策略，**When** 备份份数或时长超限，**Then** 按策略清理，且保留数量始终满足恢复需求
5. **Given** 从任一保留中的备份集恢复，**When** 恢复到干净环境，**Then** 业务校验通过（关键数据可读写、功能可用）
6. **Given** 单区故障（整台主机不可用），**When** 从备份在新主机重建，**Then** 在 RTO 内恢复服务，数据丢失 ≤ RPO
7. **Given** 一次切换（含数据库），**When** 切换完成，**Then** 数据一致性经过校验脚本验证并记录
8. **Given** 一份 DR 预案，**When** 审阅，**Then** 含场景清单、决策人、切换与恢复步骤、通信方式、外部联系人、责任人、版本号与更新日期
9. **Given** 一次 DR 演练，**When** 演练完成，**Then** 记录 RTO 与 RPO 的**实测值**，覆盖数据丢失与区域不可用两类场景
10. **Given** 演练发现的问题，**When** 整改，**Then** 有闭环记录（发现 → 责任人 → 修复 → 验证）
11. **Given** 对外证书剩余有效期 ≤ 30 天，**When** 检查，**Then** 自动续期已执行或告警已触发，续期记录可查
12. **Given** 域名与证书清单，**When** 审阅，**Then** 每项含责任人、用途、到期时间，且证书链与协议被外部拨测校验
13. **Given** 关键资源（磁盘、CPU、内存、MongoDB 连接数、队列深度），**When** 水位超阈值，**Then** 分级告警触发并可追溯到负责人
14. **Given** 一份容量模型，**When** 换算业务量，**Then** 可得出资源需求与扩容触发点
15. **Given** 一份值班表，**When** 检查任意时段，**Then** 有明确值班人且联系方式经演练验证可达
16. **Given** 一次告警升级，**When** 升级发生，**Then** 升级路径、各层级响应时限明确，交接与在办事项有记录

### Edge Cases

- 业务容器被设为 `read_only` 但服务需要写日志或临时文件 → 必须显式挂载 `tmpfs` 并限定大小，不得为图省事放开整个根文件系统
- 非 root 用户写不进去既有命名卷（卷由 root 预创建，权限为 `755`） → 容器启动时用 `init` 容器 `chown`，不得回退到 root 运行
- 基础镜像切到 `distroless` 导致缺少 CA 证书或 shell → 保留 `slim-bookworm` 并显式安装 `ca-certificates`，不追求极致精简
- 灰度分流依赖 nginx，但当前 nginx 同时是入口反代与 dsh-runtime 反代 → 灰度只作用于业务服务（`chat-api` / `admin-api` / `document-api`），基础设施与 dsh-runtime 不参与灰度
- 回滚代码但数据库已收缩（drop 了旧列） → 不可逆，必须在扩展-收缩流程中明确禁止在未完成收缩前回滚
- 迁移执行中发生回滚 → 迁移必须幂等且可前向修复，不得假设"回滚代码就会回滚数据"
- 备份集加密密钥丢失 → 备份等同废纸；密钥与备份集**必须异地存放**，且密钥可用性是 DR 演练的必测项
- 单区故障时备份在新主机重建，但 MongoDB 无副本集 → RTO 取决于备份恢复时长，必须在预案中如实写明，不得承诺"秒级切换"
- 证书自动续期需要域名控制（ACME）→ 首期若客户使用自有证书，退化为阈值告警 + 手工更换流程，不得假装已自动续期
- 特性开关无人清理，代码分支永久残留 → 到期告警 + 属主负责；属主离职时需有属主转移流程
- 检查单被"全套勾选但不写执行人"糊弄 → 检查单格式强制每项有执行人字段，空值视为未通过
- 演练只在 mock 上通过（现有 `test_backup_restore_rollback.sh` 把 Docker 调用全部 mock） → 必须补一次真实环境演练，mock 结果不得计入 RTO/RPO 实测值

## Requirements *(mandatory)*

### Functional Requirements

**部署安全基线（US1）**

- **FR-001**: 全部运行镜像（`chat-api` / `admin-api` / `document-parser` / `gateway` / `admin-web` / `user-web`）MUST 定义非特权用户并在启动前切换 `USER`，MUST NOT 以 root 运行
- **FR-002**: 运行镜像 MUST 基于最小化基础镜像（`slim` / `distroless` 类），MUST NOT 包含构建工具、测试文件与源码缓存
- **FR-003**: 镜像分层数量与总体积 MUST 有基线记录，超出基线阈值 MUST 告警
- **FR-004**: 业务容器 MUST 设置 `read_only: true`；所有必要的写入路径 MUST 显式挂载 `tmpfs`（限定大小）或命名卷并说明用途
- **FR-005**: 业务容器 MUST 设置 `cap_drop: [ALL]` 且仅按需追加 `cap_add`，MUST 启用 `no-new-privileges: true`
- **FR-006**: 全部基础设施（网络、数据库、缓存、向量库、队列、运行时）MUST 由代码定义（`docker-compose.yml` + `deploy/`），变更 MUST 经评审并附带计划输出与实际变更的对照
- **FR-007**: 各环境配置清单 MUST 可枚举，字段至少含键名、用途、是否必填、取值来源、默认值、允许取值范围，且与代码中的配置读取点一一对应
- **FR-008**: 密钥 MUST NOT 入库（含 `.env` 文件）；MUST 通过 `deployment-secrets` 卷或外部密钥源注入，仓库仅保留 `.env.example`
- **FR-009**: 配置变更 MUST 可审计（操作者、时间、旧值 → 新值、受影响服务），且 MUST 可回滚到任一历史版本
- **FR-010**: 未纳管的手工变更 MUST 可被检出（漂移检测比对运行中容器实际配置与 `docker-compose.yml` 声明）
- **FR-011**: 部署流程 MUST 拒绝部署配置中未在清单登记却为必填的键，并指出缺失键名

**制品与可追溯性（US2）**

- **FR-012**: 线上运行的镜像 digest MUST 与流水线产物一致，不一致 MUST 告警
- **FR-013**: 制品 MUST 携带语义化版本号、git commit SHA 与构建时间三项元数据
- **FR-014**: 各环境部署 MUST 使用同一制品，环境差异 MUST 仅存在于配置层
- **FR-015**: 缺失或非法配置 MUST 导致启动失败，日志 MUST 指出具体键名与期望取值范围，MUST NOT 进入半初始化状态
- **FR-016**: 部署 MUST 支持 dry-run 输出计划 diff 供预审，实际执行 MUST 与计划一致，偏离 MUST 被报告
- **FR-017**: 发布制品 MUST 可从发布说明一键安装并通过最小可用性验证
- **FR-018**: 制品晋级（candidate → promoted）MUST 有流水线记录，含晋级动作、执行者与时间
- **FR-019**: 制品 MUST 有完整性校验（digest 校验和或签名），部署前 MUST 验证

**灰度与回滚（US3）**

- **FR-020**: 新版本 MUST 支持按比例灰度（默认 `1% → 10% → 50% → 100%`），每档 MUST 有观察窗口与校验点
- **FR-021**: 灰度期间 MUST 支持新旧版本在同一指标维度（错误率、延迟、吞吐）的并排对比
- **FR-022**: 自动回滚条件 MUST 明确定义（触发指标 + 阈值 + 观察时长），MUST 在预发环境实际验证过并留存记录
- **FR-023**: 回滚流程 MUST 存在且 MUST 经过真实环境演练（不得以 mock 演练结果替代），演练记录可查
- **FR-024**: 数据变更与代码回滚的兼容性 MUST 有明确结论，不可逆变更 MUST 有迁移脚本兜底
- **FR-025**: 回滚耗时 MUST 满足约定目标（T1 级回滚 ≤ 约定分钟数），且 MUST 有实测记录
- **FR-026**: 回滚后关键指标 MUST 恢复至回滚前基线，恢复过程 MUST 有校验记录

**特性开关与发布管理（US4）**

- **FR-027**: 特性开关 MUST 登记属主、默认值、到期日期与清理计划四项
- **FR-028**: 特性开关到期 MUST 发出清理告警，属主离职时 MUST 有属主转移流程
- **FR-029**: 数据库变更 MUST 先于依赖它的代码发布
- **FR-030**: 破坏性变更 MUST 使用扩展-收缩（expand/contract）多版本流程，三个版本 MUST 互相兼容
- **FR-031**: 迁移执行 MUST NOT 阻塞线上服务，长事务 MUST 拆分或异步执行，迁移 MUST 幂等
- **FR-032**: 发布检查单 MUST 覆盖配置差异（各环境）与依赖差异（镜像 digest、运行时版本）
- **FR-033**: 发布检查单每项 MUST 有执行人与明确结论（通过 / 不适用并附理由），空值 MUST 视为未通过

**持续运行与灾备（US5）**

- **FR-034**: 备份 MUST 按策略自动执行（周期、目标窗口、失败告警），最近一次成功时间 MUST 可查
- **FR-035**: 备份 MUST 加密，访问 MUST 受控；加密密钥 MUST 与备份集异地存放
- **FR-036**: 备份保留策略 MUST 满足恢复与合规需求（保留份数、时长、过期清理），清理后剩余份数 MUST 仍满足恢复需求
- **FR-037**: 备份 MUST 可被实际恢复并通过业务校验，恢复演练 MUST 有记录
- **FR-038**: 服务 MUST 具备跨可用区部署能力，单区故障（整台主机不可用）时 MUST 能在 RTO 内恢复存活（首期以"备份 + 新主机重建"达成）
- **FR-039**: 数据库与缓存 MUST 具备跨区切换能力（首期：MongoDB 副本集 + 从备份重建，Redis 接受数据丢失并声明 RPO）
- **FR-040**: 流量切换手段与执行权限 MUST 明确（谁可切、如何切、如何验证切换成功）
- **FR-041**: 切换后数据一致性 MUST 经过校验脚本验证并留存记录
- **FR-042**: MUST 存在书面 DR 预案，含场景清单、决策人、切换与恢复步骤、通信方式、外部联系人、责任人、版本号与更新日期
- **FR-043**: DR 演练 MUST 有记录，含 RTO 与 RPO 的**实测值**
- **FR-044**: DR 演练 MUST 覆盖数据丢失与区域不可用两类场景
- **FR-045**: 演练发现的问题 MUST 有整改闭环（发现 → 责任人 → 修复 → 验证）
- **FR-046**: 对外证书 MUST 在到期前自动续期，或 MUST 设置阈值告警（剩余 ≤ 30 天）；续期或告警记录 MUST 可查
- **FR-047**: 域名与证书清单 MUST 含责任人、用途、到期时间三项
- **FR-048**: 证书链与协议配置 MUST 被外部拨测校验（不得仅依赖本机检查）
- **FR-049**: 关键资源水位（磁盘、CPU、内存、MongoDB 连接数、队列深度）MUST 有监控与分级告警
- **FR-050**: 容量模型与业务量的换算关系 MUST 可查，含扩容触发点
- **FR-051**: 值班表 MUST 覆盖全部时段且无空档，联系方式 MUST 经演练验证可达
- **FR-052**: 告警升级路径与各层级响应时限 MUST 明确；值班交接与在办事项 MUST 有记录

### Key Entities

- **制品（Artifact）**: 一个可部署的不可变镜像集合。属性：语义化版本、git commit SHA、构建时间、镜像 digest、所属发布、晋级状态（candidate / promoted）。
- **环境配置清单（Env Config Manifest）**: 每个环境（dev / staging / prod）的配置键登记。属性：键名、用途、是否必填、取值来源、默认值、允许取值范围、对应代码读取点。
- **漂移检测报告（Drift Report）**: 运行中容器实际配置与 `docker-compose.yml` 声明的差异。属性：服务名、配置项、声明值、实际值、检出时间。
- **灰度计划（Canary Plan）**: 一次灰度发布的推进计划。属性：版本号、档位比例序列、每档观察窗口、校验点、责任人。
- **回滚记录（Rollback Record）**: 一次回滚的完整记录。属性：触发原因（人工 / 自动）、触发指标与阈值、开始与结束时间、实测耗时、回滚后关键指标、是否恢复基线。
- **特性开关（Feature Flag）**: 一个可独立启停的功能开关。属性：开关名、属主、默认值、到期日期、清理计划、覆盖代码分支位置。
- **迁移脚本（Migration）**: 一次数据库变更的可执行脚本。属性：版本、顺序、是否幂等、可逆性（可回滚 / 不可逆）、依赖的代码版本区间。
- **备份集（Backup Set）**: 一次备份的全部产物。属性：时间戳、卷清单、SHA256SUMS、加密状态、版本与 commit 标记、保留期、校验状态。
- **DR 预案（DR Plan）**: 书面灾难恢复预案。属性：版本、更新日期、场景清单、决策人、责任人、切换步骤、恢复步骤、通信方式、外部联系人、RTO/RPO 目标。
- **演练记录（Drill Record）**: 一次演练的实测记录。属性：演练日期、场景、RTO 实测值、RPO 实测值、发现问题清单、整改闭环状态。
- **值班表（On-call Roster）**: 覆盖全部时段的排班。属性：时段、值班人、联系方式、升级路径、交接记录。
- **证书清单（Certificate Inventory）**: 全部对外域名与证书。属性：域名、证书有效期、责任人、用途、续期方式、外部拨测状态。

## Non-Goals *(mandatory)*

- **不引入 Kubernetes**：首期部署形态仍是 Docker Compose 单机部署，灰度通过 nginx 分流实现，不做编排层替换。
- **不实现多区域灾备（multi-region active-active）**：首期以单区域 + 可验证备份恢复达成 RTO/RPO 承诺，跨可用区能力以 MongoDB 副本集 + 备份重建方式提供，不做异地多活。
- **不实现全自动扩缩容**：扩容流程与触发点以文档和告警形式提供，由人工执行；自动伸缩不在本特性范围。
- **不重建既有制品与配置机制**：QF-811~815 已 `pass` 的实践（同制品、配置与代码分离、缺失配置启动失败）只加固为强制门禁，不重写。
- **不引入 Vault 作为强制依赖**：外部密钥源在 FR-008 中是可选路径，首期以 `deployment-secrets` 卷满足密钥不入库要求。
- **不追求 `distroless` 基础镜像**：保留 `slim-bookworm` 并显式安装 `ca-certificates`，避免为极致精简引入运维复杂度（见 Edge Cases）。
- **不追求全量服务灰度**：基础设施（mongo / redis / weaviate / dsh-runtime）不参与灰度，仅业务服务参与。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `docker inspect` 全部业务容器，`User` 非 `0`、`ReadonlyRootfs=true`、`CapDrop=["ALL"]`、`NoNewPrivileges=true` 四项全绿（覆盖 QF-818 fail 与 QF-819~820 blocked）
- **SC-002**: 配置清单登记的键与代码配置读取点一一对应，无未登记必填键；一次配置变更可在审计中查到操作者、时间、旧值→新值
- **SC-003**: 漂移检测在人工注入变更后可 100% 检出
- **SC-004**: 线上任一容器 digest 可反查到流水线发布记录与 git commit；删除任一必填配置键启动即以非零码失败并指明键名
- **SC-005**: 灰度 1%→10%→50%→100% 四档可执行，每档观察窗口内新旧版本指标可并排对比
- **SC-006**: 自动回滚条件在预发环境实际触发过；真实环境回滚演练实测耗时 ≤ 约定目标，回滚后关键指标恢复基线
- **SC-007**: 特性开关四项登记齐全且到期可告警；一次含 schema 变更的发布中数据库变更先于代码落地，且代码回滚后旧版本仍可运行
- **SC-008**: 发布检查单每项均有执行人与结论，无空值项
- **SC-009**: 自动备份最近一次成功时间在约定窗口内；备份已加密且密钥异地；恢复演练业务校验通过
- **SC-010**: 单区故障（整台主机不可用）后在 RTO 内恢复服务，数据丢失 ≤ RPO；DR 预案与演练记录含 RTO/RPO 实测值并覆盖数据丢失与区域不可用两类场景
- **SC-011**: 证书剩余 ≤ 30 天时告警或自动续期触发；域名与证书清单 100% 含责任人、用途、到期时间
- **SC-012**: 值班表零空档；告警升级路径与各层级响应时限明确且经演练验证

## Assumptions

- 部署形态为单机 Docker Compose（`docker-compose.yml` 已定义 13 个服务、10 个命名卷，卷前缀 `movo_`），本特性不改变该形态。
- 现有 `mogo backup` / `mogo restore`（`deploy/cli/backup.sh`）已归档 8 个卷并写 SHA256SUMS 与版本/commit 标记，QF-837 已 `pass`；US5 在此基础上补自动化、加密、保留策略与真实演练，不重写备份函数。
- `scripts/test_backup_restore_rollback.sh` 目前把 Docker 调用全部 mock，其结果**不计入** RTO/RPO 实测值；US3 与 US5 均需一次真实环境演练。
- 首期单区域意味着"跨可用区"以 MongoDB 副本集 + 备份重建达成，不承诺秒级切换；Redis 数据在切换中视为可丢失（RPO 按 Redis 自身持久化配置如实声明）。
- 灰度分流依赖现有 nginx（`deploy/docker/nginx.conf`），nginx 同时承担入口反代与 dsh-runtime 反代，因此灰度作用域限定为业务服务。
- TLS 当前为手工放置（`deploy/tls/README.md` 要求手工拷贝 `fullchain.pem` 与 `privkey.pem`），首期退化为阈值告警 + 手工更换；ACME 自动续期作为可选增强，不作硬性成功条件。
- 与 001 gatekeeper-governance 联动：配置变更审计、发布检查单结论、演练记录均写入既有审计体系，不新建平行审计存储。
- 与 007 llm-gateway-resilience 联动：自动回滚触发的指标中，大模型调用相关的重试与超时指标复用 007 已定义口径，不重复定义。
- 42 个缺陷中 41 项 `blocked` 是"基础设施未建立"，本特性绝大多数任务是**新建**（脚本、配置模板、流水线步骤、文档、演练记录），而非修改既有业务代码；因此本特性的验收主要看"基础设施存在且可验证"，不看业务代码改动量。
