- [x] CHK002 项目归属维度是否定义？→ FR-002：`tenant_id + user_id`（D1 纯个人项目，不引入成员表）
- [x] CHK003 默认项目的创建时机与幂等性是否定义？→ FR-003：按 `(tenant_id, user_id)` 幂等 upsert；SC-004 用"连跑两次写 0 条"作判据
- [x] CHK004 会话的项目归属是否覆盖两类会话？→ FR-004：code 会话 = workspace id，web 会话 = `"default"`，新会话不留空
- [x] CHK005 项目维度"没数据"的根因与修法是否写清？→ FR-006：模型网关令牌缺 `user_id` + 网关未反查绑定；这是 plan.md 标注的"唯一卡点"，不是靠回填能补的
- [x] CHK006 归档的触发方与判定依据是否定义？→ FR-009 + spec Edge Case 4：**只由客户端对账触发**，服务端不扫描（目录是否存在只有客户端知道）
- [x] CHK007 回填范围与失败处理是否定义？→ FR-008：全量（D4）、分批、可重入、失败清单、断点续跑
- [x] CHK008 迁移期读写兼容是否定义？→ FR-011：读侧 `project_id or workspace_id or "default"`；plan.md 明确"P0 不改读写行为"

## 四、边界与歧义

- [x] CHK018 同一目录被两个项目绑定是否允许？→ Edge Case 1：允许，服务端不校验路径唯一性（路径不上云，无法校验）
- [x] CHK019 默认项目被误归档/删除如何处理？→ Edge Case 3 + FR-003：不可归档、不可删除，服务端拒绝
- [x] CHK020 多设备场景下归档判定是否定义？→ Assumptions：以"最后一次对账的设备"为准，不要求全设备一致（已显式接受该近似）
- [ ] CHK021 **回填分批大小与时间窗未定**：tasks T002 说"由 `agent_kernel_bindings` 覆盖率决定分批大小"，但 spec 未给上界与超时预算。需在 T002 执行后回填（参考 042 R-5 的 5000 截断口径）
- [ ] CHK022 **集合改名的停机窗口未量化**：spec Edge Case 6 只说"停旧实例 → 改名 → 起新实例"，未定义可接受停顿时长与回滚方式（改名可逆，但回滚需再次停实例）。需在发布方案评审时定值
- [ ] CHK023 **归档后"恢复"的判定未定**：US2 场景 3 说"目录恢复 → 回 active"，但未说明由谁触发、是否需要用户确认。倾向"客户端对账自动恢复"，需产品确认

## 五、需求质量结论

14 项原生达标（CHK001–CHK020 中的 20 条已勾选），3 项待定（CHK021 回填参数、CHK022 停机窗口、CHK023 恢复触发方）。

三项待定**均不阻塞 spec 定稿**：它们属于实施参数与发布方案，不影响 FR 的可执行性；但 CHK021 会影响 T017–T020 的排期，CHK022 会影响上线计划，建议在 `/speckit-implement` 前先补。

**已知的诚实占位**：spec 未虚构"回填耗时"数字——plan.md 的"1 万会话 10 分钟"是估算目标，不是实测，T002 执行后应替换为真实值。
