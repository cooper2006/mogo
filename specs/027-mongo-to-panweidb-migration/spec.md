# Feature Specification: MongoDB → PanWeiDB 数据后端迁移

**Feature Branch**: `027-mongo-to-panweidb-migration`

**Created**: 2026-10-13

**Status**: Draft（**R1 基础设施已落地**；R2 接线、R3 关系化待办）

**Input**: 用户要求「新建一个分支迁移 mongo 到 panweidb」；目标库已在 OrbStack 中就绪并给出账号。

## 背景与现状

MOVO 三个后端服务（admin-api / chat-api / document-parser）当前全部以 MongoDB 作为
唯一业务数据存储。用户要求把数据存储迁移到 **PanWeiDB**（中国移动基于 openGauss 内核
自主研发的企业级关系型数据库）。

**本特性的关键约束来自实测，而非假设**：

1. **PanWeiDB 不提供 MongoDB 线协议兼容**。（线协议级兼容是金仓 KingbaseES 的能力，
   PanWeiDB 没有。）因此迁移只有两条路：**自建兼容层**，或把全部调用点改写成 SQL。
2. **规模决定了不能一次性改写**：3 个服务、149 个文件、**612 处数据访问入口**、
   **103 个数据集合**。逐一改写为 SQL 是数周级工作，且回归面覆盖整个后端。
3. **存储范式不同**：MongoDB 是文档模型（动态字段、嵌套结构），PanWeiDB 是关系模型。
   迁移不是换连接串，而是模型映射。

**已确认的三条路线决策（2026-10-13，用户拍板）**：

- **兼容层先行**：在数据访问入口之下实现一个形状与现有驱动一致的门面，使既有业务
  代码无需改写即可读写新库；先跑通全链路，再按域逐步关系化。
- **开关式回滚**：用环境变量在后端之间切换，默认保持原后端；出问题即时切回，
  **不需要回滚代码**。
- **分阶段推进**：本特性首期只交付基础设施与迁移工具，不触碰业务调用点。

## User Scenarios & Testing *(mandatory)*

用户故事按依赖顺序排列。**US1 是其余故事的前置条件**（没有可切换的后端，
搬迁与读写都无处落地）。

### User Story 1 (P1) — 数据后端可开关切换，默认行为完全不变

运维通过一个环境变量决定服务使用哪个数据后端。**未显式开启时，系统行为与迁移前
逐字节等价**——这是本特性能被安全引入的前提。

**Acceptance Scenarios:**

1. **Given** 环境变量未设置，**When** 服务启动并处理请求，**Then** 走原后端，
   配置解析、连接建立、健康检查输出与迁移前一致。
2. **Given** 环境变量指向新后端且连接参数完整，**When** 服务启动，**Then** 连接池
   建立成功、健康检查显示新后端可达。
3. **Given** 环境变量指向新后端但连接参数缺失或不可达，**When** 服务启动或探活，
   **Then** 给出可操作的错误信息，**不静默降级到原后端**（静默降级会让运维
   以为已切换而实际没有）。
4. **Given** 运行中需要回退，**When** 把环境变量改回原后端并重启，**Then** 系统
   恢复原行为，**无需改动任何代码**。

**Why this priority**: 这是整个迁移的安全阀。没有它，任何后续步骤都不可回滚。

**Independent Test**: 不启动新库，仅切换环境变量并观察启动日志、健康检查输出与
连接目标；两个方向（默认 / 切换）各验证一次。

---

### User Story 2 (P1) — 既有业务代码无需改写即可读写新后端

业务代码里已有的数据读写语句（查询、写入、更新、删除、计数、去重、索引声明）
在新后端上保持原有语义，**调用点不做修改**。这决定了迁移的可行性与成本。

**Acceptance Scenarios:**

1. **Given** 一个按字段等值查询的调用点，**When** 在新后端执行，**Then** 返回同一条文档。
2. **Given** 一个带嵌套字段路径的更新（如 `{"$set": {"a.b": 1}}`），**When** 父对象
   尚不存在，**Then** 中间层被创建且同级既有字段**不被抹掉**。
3. **Given** 一个带操作符的查询（集合包含、范围比较、正则、存在性、逻辑组合），
   **When** 在新后端执行，**Then** 结果集与文档数据库一致（含「字段缺失」的边界语义）。
4. **Given** 一个数组追加操作（含去重语义），**When** 在新后端执行，**Then**
   数组内容与文档数据库一致。
5. **Given** 一个索引声明（单字段或复合），**When** 服务启动时执行，**Then**
   索引被创建且不因目标表尚未存在而失败。

**Why this priority**: 这是「兼容层先行」路线的全部价值所在。若调用点必须改写，
本路线退化为全量重构。

**Independent Test**: 用同一组用例分别对文档数据库与新后端执行，断言结果集与
更新后的文档结构一致。

---

### User Story 3 (P1) — 存量数据可搬迁、可校验、可重跑

运维能把现有数据搬迁到新库，并能独立验证「搬迁是否完整」。

**Acceptance Scenarios:**

1. **Given** 存量数据与目标库，**When** 执行演练模式，**Then** 只统计不写库，
   输出每个集合的待搬文档数。
2. **Given** 已搬迁部分数据，**When** 重新执行搬迁，**Then** **不产生重复数据**，
   已写入的行被覆盖为最新值（幂等）。
3. **Given** 搬迁完成，**When** 执行校验模式，**Then** 逐集合比对源库与目标库的
   文档数，不一致的集合被明确列出。
4. **Given** 搬迁后的数据，**When** 通过 US2 的门面读取，**Then** 字段值、嵌套结构、
   数组内容与源库一致，且能继续被更新。
5. **Given** 搬迁过程被中断，**When** 重新执行，**Then** 结果与未中断时一致。

**Why this priority**: 数据搬迁不可逆且不可丢失，必须先有可校验的手段。

**Independent Test**: 用一份可控的小规模数据集完成「演练 → 搬迁 → 重跑 → 校验 →
门面回读」全链路，断言各步输出。

---

### User Story 4 (P2) — 建表可自动生成、可巡检

新库的表结构必须显式创建（不像文档数据库那样首次写入隐式建集合）。运维需要
一个能**从代码推导出所需表**并**巡检缺失**的手段，避免启动期因表缺失而失败。

**Acceptance Scenarios:**

1. **Given** 代码中散落的集合名声明，**When** 执行生成器，**Then** 输出幂等的
   建表语句，覆盖代码实际引用的全部集合。
2. **Given** 已建表的目标库，**When** 执行巡检，**Then** 明确报告「期望 N 张 /
   已有 M 张」并列出缺失项。
3. **Given** 一个尚未建表的集合，**When** 业务代码首次写入，**Then** 表被自动创建，
   写入成功（不要求运维提前建表）。

**Why this priority**: 缺表会让服务启动直接失败；但它是可自动化的机械工作，
优先级低于 US1–US3。

**Independent Test**: 在空 schema 上执行生成器 → 建表 → 巡检，再对一个未建表的
集合直接写入。

---

### User Story 5 (P2) — 未覆盖能力显式失败，而非静默出错

兼容层不可能一次覆盖全部能力。**未覆盖的能力必须在调用时立刻失败并指出位置**，
绝不能静默返回空结果或错误数据——那会让问题延迟到生产才暴露。

**Acceptance Scenarios:**

1. **Given** 一个兼容层尚未实现的聚合管道调用，**When** 执行，**Then** 抛出明确
   异常，异常信息指出「未实现 + 需在哪里处理」。
2. **Given** 一个尚未实现的操作符，**When** 执行，**Then** 同样显式失败。
3. **Given** 已实现的正常调用，**When** 执行，**Then** 不因上述机制产生误报。

**Why this priority**: 这是把「未知缺口」转化为「可枚举清单」的机制，直接决定 R2
的工作量估算是否可信。

**Independent Test**: 对已知未覆盖的能力逐个调用并断言异常类型与信息内容。

---

### Edge Cases

- **嵌套路径的父对象不存在时更新**：必须创建中间层且保留同级字段（文档数据库
  的深合并语义）；不能静默丢更新，也不能整块覆盖父对象。
- **查询「字段不存在」的取反语义**：文档数据库中「字段缺失」满足「不等于某值」，
  关系模型下需显式处理，否则结果集偏小。
- **标识符类型**：文档数据库的主键是对象类型，关系模型的 JSON 字段只能落成字符串。
  迁移后按字符串比较仍可命中，但**按对象比较的调用点会失效**，需在 R2 逐点核对。
- **正则方言差异**：文档数据库用 PCRE，目标库用另一种正则方言，复杂断言需改写。
- **唯一索引语义**：文档数据库的稀疏/部分索引在关系模型下没有直接对应物。
- **空集合**：源库中零文档的集合也必须建表并计入校验（否则「漏建表」会被
  计数校验掩盖）。
- **中文字段值与超长文本**：必须保证编码往返一致。
- **并发首次写入同一集合**：隐式建表必须幂等且可并发。

## Requirements *(mandatory)*

### Functional Requirements

**后端选择与生命周期**

- **FR-001**: 系统 MUST 支持通过环境变量选择数据后端，取值至少包含「原后端」与
  「PanWeiDB」两种；变量未设置时 MUST 等价于「原后端」。
- **FR-002**: 系统 MUST 在未显式选择新后端时，保持配置解析、连接建立、健康检查
  输出与迁移前完全一致（不得引入额外连接或额外往返）。
- **FR-003**: 系统 MUST 为三个后端服务提供统一的后端初始化与关闭入口，供启动与
  关闭钩子调用；关闭 MUST 幂等。
- **FR-004**: 选择新后端但连接参数缺失或目标不可达时，系统 MUST 显式失败并给出
  可操作的错误信息，**MUST NOT** 静默回退到原后端。
- **FR-005**: 系统 MUST 在连接池初始化前校验连接参数完整性；连接池 MUST 支持
  最小/最大连接数与连接超时配置。
- **FR-006**: 系统 MUST 为三个服务提供连接池健康探测；异步服务 MUST 使用异步探测，
  避免为探活额外建立同步连接池。

**兼容门面**

- **FR-007**: 系统 MUST 提供一个形状与现有数据访问驱动一致的门面对象，使
  「按集合取句柄 → 调用方法」的既有写法无需修改即可在新后端工作。
- **FR-008**: 门面 MUST 支持以下操作并保持原语义：单条查询、条件查询（含排序/
  分页/投影）、单条与批量写入、整体替换、单条与批量更新、单条与批量删除、
  计数、去重取值、索引声明（单字段与复合）。
- **FR-009**: 门面 MUST 支持以下查询算子：等值、不等值、范围（含数值与文本）、
  集合包含/排除、字段存在性、正则（含忽略大小写）、逻辑与/或/非、数组长度、
  数组全包含。
- **FR-010**: 门面 MUST 支持以下更新算子：字段赋值、字段删除、数值增减、仅插入时
  赋值、数组追加（含批量）、数组去重追加（含批量）、取最大/最小值、置当前时间。
- **FR-011**: 门面 MUST 支持以点号表示的嵌套字段路径，用于查询与更新。
- **FR-012**: 更新嵌套路径时，若父对象不存在，门面 MUST 创建中间层**且保留父对象
  下的同级既有字段**（深合并语义）。
- **FR-013**: 门面 MUST 在查询「字段不存在」相关条件时，与文档数据库的语义一致
  （字段缺失参与不等值判定）。
- **FR-014**: 索引声明 MUST 支持单字段与复合字段，且 MUST 在目标表不存在时先建表
  再建索引，不得因缺表而失败。
- **FR-015**: 门面 MUST 在首次操作某集合时自动建表（幂等、可并发），使业务代码
  无需感知建表步骤。
- **FR-016**: 门面 MUST 对尚未实现的能力抛出显式异常，异常信息 MUST 指明「未实现
  的内容」与「应在何处处理」。

**建表与搬迁工具**

- **FR-017**: 系统 MUST 提供从代码中推导集合清单并生成幂等建表语句的工具，覆盖
  代码实际引用的全部集合（含仅出现在集合清单常量中的集合）。
- **FR-018**: 建表工具 MUST 提供连库巡检模式，报告期望表数、已有表数与缺失清单。
- **FR-019**: 系统 MUST 提供数据搬迁工具，支持演练模式（只统计不写库）。
- **FR-020**: 搬迁工具 MUST 幂等：重复执行不产生重复数据，已写入的行被覆盖为最新值。
- **FR-021**: 搬迁工具 MUST 支持校验模式，逐集合比对源库与目标库的文档数并列出
  不一致项。
- **FR-022**: 搬迁工具 MUST 只读源库，MUST NOT 修改或删除源库数据。
- **FR-023**: 搬迁工具 MUST 支持跳过已完成集合（续跑），进度可持久化。

**文档与可维护性**

- **FR-024**: 本特性 MUST 产出一份权威迁移方案文档，包含：目标库实测事实、
  规模盘点、完整映射规则、覆盖范围与缺口清单、分阶段计划、风险清单、验收标准。
- **FR-025**: 映射规则中**不得使用目标库不支持的函数或运算符**；该限制 MUST
  以可执行的守卫测试固化，防止后续修改引入违规用法。
- **FR-026**: 兼容门面在多个服务间重复的副本 MUST 由守卫测试保证不漂移
  （异步副本之间逐字节一致；同步副本为异步副本的机械变换结果）。
- **FR-027**: 系统 MUST 提供不依赖数据库的纯逻辑单元测试，覆盖映射规则与
  「占位符数量等于参数数量」这一不变量。
- **FR-028**: 三个服务的依赖清单 MUST 声明新驱动依赖，且带哈希的锁定文件 MUST
  能通过完整性校验安装。

**跨特性能力保全（不得因迁移而退化）**

- **FR-029**: 系统 MUST 在新后端上保留**按租户批量删除数据**的能力，使既有的租户
  销毁流程（含其分阶段执行与失败记录语义）行为不变。
- **FR-030**: 系统 MUST 在新后端上保留**审计与业务数据的隔离能力**：支持把审计数据
  指向独立的 schema；未配置独立 schema 时 MUST 回退到业务 schema 并保持可用
  （与既有「审计库未配置时回退业务库」的行为一致）。
- **FR-031**: 系统 MUST 在新后端上保留**连接池耗尽与不可达时的可用性语义**：存储
  抖动 MUST NOT 导致管理面账号被整体锁死或请求被无限阻塞。
- **FR-032**: 系统 MUST 在新后端上保留**按时间清理过期数据**的能力（如审计日志
  保留期、租户墓碑回收），使既有的保留期策略不因后端更换而失效。

### Key Entities

- **数据集合（Collection）**：逻辑上的一组同构文档。迁移后映射为一张表，
  表名等于集合名。集合清单是迁移范围的事实来源。
- **文档（Document）**：集合中的一条记录，含主键与任意嵌套字段。迁移后完整保存在
  一个 JSON 类型的列中，主键与租户标识额外提升为独立列。
- **数据后端（Data Backend）**：可选的数据存储实现。同一时刻只有一个生效，
  由环境变量决定。
- **兼容门面（Compat Facade）**：位于数据访问入口与具体后端之间的一层，
  对外暴露与现有驱动一致的接口，对内把调用翻译为目标库的查询语言。
- **迁移进度（Migration Progress）**：记录每个集合的搬迁状态与文档数，
  用于续跑与审计。
- **后端健康快照（Backend Health Snapshot）**：健康检查输出的后端信息，
  含后端名、连接目标（脱敏）与可达性。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 环境变量未设置时，三个服务的启动路径与健康检查输出与迁移前一致；
  不新增任何到新库的连接。
- **SC-002**: 兼容门面在真实 PanWeiDB 上的端到端用例通过率 **100%**：
  异步服务 ≥ 60 项、同步服务 ≥ 25 项。
- **SC-003**: 存量数据搬迁后，**全部集合**的源库与目标库文档数一致，
  不一致项为 **0**。
- **SC-004**: 搬迁工具重复执行后目标库文档数**不增加**（幂等验证）。
- **SC-005**: 建表工具覆盖代码引用的全部集合，缺失项为 **0**；103 张表的建表
  耗时在 **10 秒**内完成。
- **SC-006**: 未覆盖能力的调用**100%** 抛出显式异常，无静默降级路径。
- **SC-007**: 三个服务的带哈希依赖锁定文件均能通过完整性校验安装，失败数为 **0**。
- **SC-008**: 回滚操作**不需要改动代码**，仅需改环境变量并重启。
- **SC-009**: 按主键或租户标识过滤的查询 MUST 走索引；兼容门面产生的查询在执行
  计划中**不出现全表扫描**（对 103 张表抽样验证）。
- **SC-010**: 迁移后既有的租户销毁流程与审计保留期策略 MUST 仍可完整执行，
  退化项为 **0**。

## Non-Goals

- **不追求** 首期把 612 处调用点改写为 SQL——那是本特性的后续阶段（R3），
  且仅对确认存在性能瓶颈的热点集合执行。
- **不追求** 在目标库上复刻文档数据库的全部查询语言（聚合管道、地理查询、
  全文检索、变更流等）。未覆盖项按 FR-016 显式失败，在 R2 按实际使用量逐点处理。
- **不引入** 双写或双读（迁移期间的一致性由「先搬迁、后切换、可回滚」保证，
  双写会引入难以验证的一致性问题）。
- **不改变** 对外 API 契约、前端行为、鉴权与权限模型。
- **不替换** 向量库与缓存（Weaviate / Redis），它们不在本次迁移范围内。

## Assumptions

- 目标库版本与兼容模式在迁移期间保持不变（该参数不可运行时修改，见 plan.md 的
  实测事实）。若目标库版本升级导致能力变化，需重新评估 plan.md 中的约束。
- 目标库以容器方式在本地/内网可达，且具备一个可创建 schema 的账号。
- 迁移窗口内源库可读；不要求停机（搬迁工具只读源库）。
- 目标库的表结构固定为「主键 + 租户标识 + 文档 + 时间戳」四类列；**新增业务字段
  不需要 DDL 变更**，这是兼容层能低成本落地的前提。
- 现有服务的测试基础设施（pytest）可用于新增的纯逻辑单测与守卫测试。
- 三个服务各自独立部署，因此兼容层代码在服务间存在重复副本，由守卫测试防漂移。
