# ADR-6：027 切流后数据缺口处置——补同步增量 vs 直接回滚；决策前冻结放量

- **状态**：Accepted（active）
- **日期**：2026-10-23（决策与落库同日）
- **决策人**：cooper
- **相关特性**：`specs/027-mongo-to-panweidb-migration/`（默认后端仍是 mongo，切流尚未执行）

---

## 1. 背景（Context）

027 已交付「可切换 + 已验证能迁 + 可即时回滚」的能力，但运行栈默认仍是 mongo。切流路径上有一个**结构性分叉**：

- 一旦 mongo **停写**（全栈翻转 `MOGO_DATA_BACKEND=panweidb` 之后），panwei 成为唯一活数据源；
- 此时若要回 mongo，**mongo 缺少切流期间的新增/变更数据**——027 工具只支持 mongo→panwei **单向**，没有反向搬迁能力；
- 两种处置：**补同步增量**（先把 panwei 的增量反向补进 mongo，再回滚）vs **直接回滚**（接受缺口，分钟级恢复）。

用户拍板：**在「补同步 vs 回滚」决策作出前，不继续放量观察。**

## 2. 决策（Decision）

1. **冻结放量（默认纪律）**：决策作出前，不得继续放量——
   - 不扩大灰度域、不翻转更多服务、不提高 panwei 承载的流量比例；
   - 已处于灰度中的域/服务：**保持现状，或回退到上一个稳定态，不前进**；
   - 只读巡检（每日自动化）继续运行，为决策提供数据依据。
2. **默认处置策略：补同步增量优先**。mogo 是业务系统，会话 / 审计 / 租户数据的丢失面大，而反向补齐是一次性脚本成本——默认走「补数后再回滚」。
3. **补数的工程前提（三步，缺一不可）**：
   1. **冻结 panwei 写入**（停止切流中的服务或整体摘流）——否则增量永远追不平，补数无终点；
   2. **反向补齐 mongo**（panwei JSONB → pymongo 插入；`_id` 字符串→ObjectId 的还原按各集合主键策略处理，027 无现成工具，需临时脚本）；
   3. **切回 mongo**（`.env` 改 `MOGO_DATA_BACKEND=mongo` + `docker compose up -d`）并跑 mongo 路径回归确认。
4. **例外：直接回滚**。当缺口经业务确认可接受时（纯 dev 数据、可重放作业、极小缺口），跳过补数直接回滚——时效优先，分钟级恢复。
5. **判定与监控不变**：每日巡检的判定规则维持——某集合 `panweidb < mongo` = 数据丢失告警（回滚触发条件）；`panweidb > mongo` = 切流后预期增量，不是告警。

## 3. 后果 / 已知约束（Consequences）

- **补数窗口 = 停写窗口**：反向补齐期间 panwei 必须冻结写入，等于一次计划内可用性损失，需与业务窗口配合；这与「回滚要快」天然冲突，是补数路线的主要代价。
- **反向迁移是一次性脚本**：需处理 `_id` 类型还原、`tenant_id` 提升列、时间戳列与 JSONB 的解包；跑完即归档，不并入 027 工具链（工具链保持单向，避免范围蔓延）。
- **冻结放量的可执行判据**：灰度推进到「下一步动作 = 扩大流量/翻更多服务」时，先对照本 ADR——决策未作出就不执行该动作。
- **dev 环境的现实宽松度**：当前 dev 栈（17,785 篇 / 88 集合）若切流期写入少且可重放，直接回滚的缺口可能可接受——但这需要显式确认，不默认成立。
