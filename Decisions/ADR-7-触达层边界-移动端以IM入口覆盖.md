# ADR-7：触达层边界——移动端以 013 多 IM 入口覆盖，不单独做移动端，不做桌面端

- **状态**：Accepted（active）
- **日期**：2026-10-23（决策与落库同日）
- **决策人**：cooper
- **相关特性**：`specs/013-multi-im-entry/`（已生产接线）；`docs/MOGO-AgentOS整合方案.md`（触达层边界条目）

---

## 1. 背景（Context）

《企业 Agent OS 产品落地方案》（2026-10-15）的触达与交互层提出四种形态：网页工作台、消息机器人、开放接口、移动端。在 mogo 的 AgentOS 整合评估中，触达层呈现：

- **已具备**：user-web / admin-web（网页工作台）、013 多 IM 入口（飞书等消息机器人，已生产接线：`im_gateway.py` webhook + HMAC 签名 + 持久化会话绑定）、012 A2A（开放接口）、029 SSO 接收（外部门户免登进入）。
- **未做**：移动 Web/H5/App；桌面客户端新建。

员工侧的真实触达场景（移动办公、即时通讯内使用）与 IM 入口天然重合，而独立的移动端 / 桌面端意味着新增客户端形态、新增一套适配与发版链路、双倍治理接线成本。

## 2. 决策（Decision）

1. **移动端以 013 多 IM 入口覆盖为主**：不为移动办公单独建设 H5 / App。员工在飞书等 IM 内@bot 使用 Agent，即为 mogo 的移动触达答案；触达层对外表述统一为「网页工作台 + 消息机器人（IM）+ 开放接口」三形态。
2. **不做桌面端新建**：不为 AgentOS 整合新建桌面客户端。既有 MOGO Desktop（连接浏览器 / Code Agent）**维持现状、不扩展、不回改**，后续若其生命周期结束按常规下线流程走，不因本决策提前处置。
3. **统一门户仍建（不受本决策影响）**：移动触达收敛不等于门户收敛——应用门户 + 自助申领（整合方案 §4.6）照常立项，门户以 Web 形态交付，经 029 SSO 与 IM 入口分发。
4. **边界效力**：后续任何「移动端适配」「桌面客户端」类需求，默认回到本 ADR 重新论证，不默认开工；文章效果叙事中的「移动端」一律按 IM 入口口径解释。

## 3. 后果 / 已知约束（Consequences）

- **纯移动场景依赖 IM 客户端能力**：复杂表格 / 大屏交互在 IM 内体验受限，此类场景引导至 Web 工作台（IM 内回链跳转）；这是接受的成本，不以建 H5 方式补救。
- **IM 覆盖面 = 移动覆盖面**：新增移动触达需求（如企业微信 / 钉钉 / Slack）转化为 013 的渠道扩展，而非新客户端。
- **对外材料口径**：README / 方案文档中触达层删除「移动端」独立条目，改为「IM 入口（移动触达）」表述。
