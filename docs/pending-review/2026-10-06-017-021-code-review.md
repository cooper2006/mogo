## P1 · 设计问题（三项均已修复，10:20）

### P1-1 `sediment_session_end` 的 hook 发射是空操作 ✅ 已修复

**原状**：`app/memory/sediment.py:181-193`

```python
emit_session_end(
    HookRegistry(enabled={SESSION_END}),   # ← 每次现造一个 registry
    session_id=session_id,
    actor=owner_id,
)
```

`HookRegistry` 的作用只是 `is_enabled(event)` 判断（`registry.py:58`）。这里传入一个**当场构造、只含 SESSION_END 的空 registry**，`is_enabled` 必然为 True，于是 `emit_session_end` 返回一个 `HookEventPayload` 对象——但**没有任何订阅者消费它**，随即被丢弃。

`except Exception: pass` 还会吞掉一切，让这个空操作看起来"成功"了。docstring 里"honors the contract so the seam is complete"是**不准确的**。

**修复**：新增 `app/dsh_runtime/hooks/dispatcher.py`，补上闭环缺失的消费侧：

- `subscribe/unsubscribe/clear_subscribers/subscriber_count` —— 进程内订阅注册表（`dict` 保序，派发确定可重放）
- `dispatch(payload)` —— async-aware，同步与异步订阅者都支持；**订阅者异常隔离**（坏观察者不影响其他），失败名返回供调用方记日志
- `dispatch_session_start/end/post_tool_use/memory_commit` —— build + deliver 完整回路

刻意**不引入新基础设施**（Kafka/Redis）：009 是 hook 机制，进程内注册表已足够且可测，符合 021"不新建存储"的整体取向。

`sediment.py` 侧：注册为真实 `SessionEnd` 订阅者（`register_sedimentation_subscriber` / `ensure_registered`，幂等）；`emit_hook` 默认改 `False` —— 本函数**本身就是**消费者，再发射会重入沉淀循环。

**核心回归测试**：`test_session_end_event_actually_sediments` —— 断言 `dispatch_session_end` 后 fake store 确实收到写入（修复前该 dict 恒为空）。

### P1-2 `sessions.py` 沉淀只挂在 delete_session ✅ 已修复（用户指定优先）

**原状**：沉淀接在 `delete_session` 里，"删除会话时顺便沉淀出会话记忆"很别扭——**会话正常结束不沉淀，只在被删除时才沉淀**。

**更深的问题**（审查时进一步核实发现）：002 此前**根本没有"会话结束"这个概念** —— 无 `ended_at` 字段、无结束端点，唯一终结操作就是 `delete`。而 009 spec 明确写 SessionEnd「以 002 的会话生命周期事件为载体」。所以这不是"挂错位置"，而是**载体本身缺失**，挂哪都不对。

**修复**：

1. `session_doc` 初始化补 `"ended_at": None, "end_reason": ""`
2. 新增 `SessionPersistenceService.end_session(...)` —— 置结束状态 → 经 `dispatch_session_end` 派发 009 事件 → 触发 017 沉淀。**幂等**（已结束则直接返回不重复派发）；订阅者异常仅记日志，不回滚状态
3. 新增 `POST /sessions/{id}/end` 端点
4. `delete_session` 降级为**兜底**：仅对从未结束过的会话沉淀，经 `_SEDIMENTED` 账本去重

**核心回归测试**：`test_end_session_sediments_via_dispatcher` —— 结束会话后断言记忆写入的 `source_session_id` / `source_type` / `content`。

### P1-3 `_load_kg` 加载全图，违反"渐进式"初衷 ✅ 已修复

**原状**：`app/context_space/adapters/resource.py:157-161`

```python
store = TenantKgStore(tenant_id=tenant_id)
await store._ensure_loaded()      # 整个租户的图全量载入内存
node = store.get_node(node_id)
```

为取**一个节点**把整张图谱拉进内存（`_ensure_loaded` 一次最多拉 2000 节点 + 5000 边），只为了算 `neighbour_count` 和前 10 个邻居名；且调用私有方法破坏封装。

**修复**：`TenantKgStore` 新增公开接口 `get_node_direct(node_id, *, max_neighbours=10)` —— 直查 `kg_nodes` 单节点 + 限量拉取邻居；已加载时回退内存路径（保留未持久化 `add_node` 的可见性），db 不可用时优雅降级。适配器改用该接口。

**核心回归测试**：`test_resolve_resource_kg_does_not_load_whole_graph` —— spy `_ensure_loaded` 并断言 `bulk_loads == []`。

store = TenantKgStore(tenant_id=tenant_id)
await store._ensure_loaded()      # 整个租户的图全量载入内存
node = store.get_node(node_id)
```

为了取**一个节点**，把整张知识图谱拉进内存，只为了算 `neighbour_count` 和前 10 个邻居名。015 图谱在生产环境可能很大。

另外调用了私有方法 `_ensure_loaded()`——破坏了封装，store 若换实现就断。
